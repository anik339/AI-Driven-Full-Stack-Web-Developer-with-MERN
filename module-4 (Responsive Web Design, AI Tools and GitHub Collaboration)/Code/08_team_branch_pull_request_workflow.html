Team Branch and Pull Request Workflow

A shared repository works best when the team agrees on branch names, small commits, reviews and merge rules.

Recommended team flow

  1. Agree on the task and acceptance criteria in an issue or task board.
  2. Update your local main branch before starting.
  3. Create a short-lived feature branch for one task.
  4. Make small, meaningful commits and test your changes.
  5. Push the branch and open a pull request with a clear summary.
  6. Ask a teammate to review; respond to feedback and update the branch.
  7. Merge after required checks and approvals pass.

Common commands 

git status
git switch main
git pull
git switch -c feature/responsive-navbar

# edit files and test the result
git add path/to/changed-file.html
git commit -m "Improve responsive navigation"
git push -u origin feature/responsive-navbar

After pushing, open GitHub and create a pull request from your feature branch into the shared main branch.

Author checklist

  • Describe what changed and why.
  • Attach screenshots at mobile and desktop widths when useful.
  • Link the related issue.
  • Test the affected pages.
  • Do not commit generated files or secrets by accident.

Reviewer checklist

  • Check correctness and readability.
  • Check responsive behavior and accessibility.
  • Ask clear, respectful questions.
  • Separate blockers from optional suggestions.
  • Approve only when you understand the change.

If a merge conflict appears

  1. Read the conflict markers and compare both changes.
  2. Keep the intended parts from each version; do not blindly choose one side.
  3. Remove all conflict markers after resolving.
  4. Run the page and review the diff.
  5. Stage and commit the resolved file.

Team rules worth agreeing on

Use descriptive branch names, consistent formatting, small pull requests, clear commit messages and protected main branches when available. Never share passwords or API keys in commits. Use GitHub Issues and Discussions according to the team's needs.
